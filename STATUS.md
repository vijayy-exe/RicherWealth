## Phase 1 gaps — now closed

**MFA secret encryption.** `mfaTotpSecret` was previously stored in plaintext. `apps/api/src/auth/crypto.util.ts` implements AES-256-GCM (Node's built-in `crypto`, authenticated encryption, random 12-byte IV per call, `iv:authTag:ciphertext` hex format). `enableTotp`/`verifyTotp` in `auth.service.ts` now encrypt/decrypt through it, keyed by the new `MFA_ENCRYPTION_KEY` env var (documented in `.env.example`, generated for local dev in `apps/api/.env`, gitignored). No Prisma migration was needed — the column was already a plain `String?`. Covered by new round-trip tests in `auth.service.spec.ts` (asserts the stored value is not the plaintext secret, and that a fresh valid token still verifies after decrypt).

**WebAuthn passkey registration ceremony.** Implemented with `@simplewebauthn/server` (API) and `@simplewebauthn/browser` (web). New: `apps/api/src/auth/passkey-challenge.store.ts` (in-memory, single-use, 5-minute-TTL challenge store keyed by userId — mirrors the existing `MemoryCacheService` pattern rather than adding a Redis/DB dependency, appropriate for this single-instance deployment). `AuthService.generatePasskeyRegistrationOptions`/`verifyPasskeyRegistration` and two new controller routes (`POST /auth/passkeys/register/options`, `POST /auth/passkeys/register/verify`). Frontend: `apps/web/src/hooks/usePasskeys.ts` runs the full ceremony (fetch options → `startRegistration` → verify), and the Settings page's "Register new passkey" button (previously inert) is now wired to it, with a live list of registered passkeys and a working remove action. RP ID/origin are configurable via `WEBAUTHN_RP_ID`/`WEBAUTHN_RP_ORIGIN` (default to `localhost` / `http://localhost:3000` for dev).

**Scope note — passkey *login* is still a placeholder, intentionally.** The login page's "Sign in with Passkey" button (`apps/web/src/app/(auth)/login/page.tsx`) is unchanged — it was already self-documented as a placeholder before this work (`provider: "google", // placeholder — swap for WebAuthn`). Wiring it up requires an authentication-ceremony ↔ session-issuance design this app doesn't have yet: Supabase is the authoritative session issuer here (`SupabaseAuthGuard` validates Supabase JWTs directly), and a custom WebAuthn login would need either the Supabase Admin API or a custom JWT path to mint a session without a password — an architectural decision, not a bug fix. Registering a passkey now works end-to-end and is stored correctly; using it to log in is future work.

Fixed by giving the test an isolated in-memory cache adapter (matching the sibling specs' pattern) and flushing the poisoned key. **Any future spec for a service with `onModuleInit()`-based Redis connection logic in this repo must bypass it the same way — this class of bug is easy to reintroduce and, unlike most test bugs, corrupts real traffic, not just the test run.**

## Phase 15 — Tax Center

Capital gains (short/long-term, FIFO lot consumption), dividend tax tracking, a rules-based tax-loss-harvesting scan, versioned per-country tax config, and downloadable CSV/PDF reports. New: `apps/api/src/tax/` (6 services + controller + module + DTOs), `packages/shared-types/src/tax-config/` (US + India JSON config + Zod schema + loader), `packages/shared-types/src/tax/types.ts` (shared DTOs/report shapes), `packages/shared-types/src/calc/capital-gains.ts` (pure FIFO/term/harvesting logic), `apps/web/src/app/(app)/tax/page.tsx` + `useTax.ts`. New Prisma models: `TaxLot`, `TaxLotDisposal` (migrations `phase15_tax_center`, `phase15_tax_lot_asset_relation`).

**No lot-level cost-basis tracking existed anywhere before this phase — confirmed, not assumed.** `StockHolding`/`MutualFundHolding`/`CryptoHolding` each store only an aggregate quantity + weighted-average buy price + a single purchase date; grepped `apps/api/src/stocks` for any code writing a `Transaction` row on buy/sell — zero hits. This is genuinely new infrastructure, not a wrapper around something that already existed.

**Honest backfill, clearly labeled.** Pre-existing holdings have no real per-purchase history to recover. `TaxLotService.backfillFromExistingHoldings` creates exactly ONE synthetic lot per holding (sized to its full current quantity, dated at `purchaseDate`/`createdAt`, costed at `avgBuyPrice`/`avgNAV`), flagged `isBackfillEstimate: true` in the database and surfaced as such everywhere it's used: the capital-gains summary sets `hasBackfillEstimateData`, the frontend shows a visible banner ("Some lots in this report are backfill estimates..."), and the PDF report prints `[BACKFILL ESTIMATE]` next to every affected line. Verified live: clicking "Backfill lots" for a real test user created 7 real lots from their existing stock/crypto holdings.

**Capital gains — FIFO, short/long classification, tested against the acceptance criterion directly.** `CapitalGainsService.disposeLots` (`apps/api/src/tax/capital-gains.service.ts`) FIFO-consumes across lots (`planFifoConsumption`, `packages/shared-types/src/calc/capital-gains.ts`), classifies each consumption SHORT/LONG by the country config's threshold (`classifyHoldingTerm`), and computes the exact gain/loss. Directly tested: a lot bought 2024-01-01 and disposed 2026-06-01 at a $30/share gain on 10 shares is classified LONG with `realizedGainLoss: 300.000000`; a lot bought 2026-01-01 and disposed the same day is classified SHORT with the correct loss — both asserted in `capital-gains.service.spec.ts`, plus 17 more tests of the pure math in `packages/shared-types/src/calc/capital-gains.spec.ts`.

**Tax-loss harvesting — rules-based, reuses Phase 4/6/5's live prices, tested against the acceptance criterion directly.** `HarvestingService.getHarvestCandidates` prices open lots via `PriceSyncService.getPrice` (stocks, via the lot's linked `StockHolding.exchange`), `CryptoPriceSyncService.getPrice` (crypto), and `NavSyncService.syncSchemeNav` (mutual funds) — no fourth, parallel price fetch. `scanForHarvestCandidates` flags a lot when current price < cost basis AND the country's `lossOffsetAllowed` rule permits it — **India crypto is excluded entirely** (Section 115BBH bars offsetting a VDA loss against anything), not shown with a misleading $0 offset. Verified live: a real test user's backfilled AAPL lot (cost basis $150,000, now worth $4,818.75) and Dogecoin lot correctly surfaced as harvesting candidates with real current prices and an estimated tax saving. Directly tested with a synthetic underwater holding (bought at 50, now 30 → flagged, correct loss amount) per the acceptance criterion, plus a gain-holding exclusion case and an India-crypto exclusion case.

**Country tax config — versioned JSON, not hardcoded, adding a country is a config change.** `packages/shared-types/src/tax-config/{us,india}.json`, Zod-validated at import time (`schema.ts`). ## Phase 16 — Zero-Knowledge Document Vault (2026-09-05)

Client-side AES-256-GCM encryption (browser's native `crypto.subtle`) before any document byte leaves the client — the server and Supabase Storage only ever see ciphertext. New: `apps/api/src/vault/` (controller/service/DTOs), `packages/shared-types/src/vault/{crypto,types}.ts`, `apps/web/src/app/(app)/vault/page.tsx` + `useVault.ts`. New Prisma model `VaultDocument` + four new `User` fields (`vaultKeySaltB64`, `vaultCanaryB64`, `vaultCanaryIvB64`, `vaultSetupAt`) (migration `phase16_vault`).

**Architecturally distinct from Phase 1/15's document storage — stated explicitly so nobody downstream conflates them.** `asset-documents` (Phase 1) and `tax-documents` (Phase 15) upload PLAINTEXT over TLS: this API server and Supabase Storage both see file content (Supabase-managed at-rest encryption only, no application-level layer). The vault's `vault-documents` bucket (new, auto-provisioned by the same `StorageService.onModuleInit` idempotent-bucket-check pattern Phase 15 introduced) receives ONLY AES-256-GCM ciphertext the browser produced before `StorageService` is ever called — `apps/api/src/vault/vault.service.ts` never imports `packages/shared-types/src/vault/crypto.ts` (confirmed by grep) and has no code path that could decrypt anything even if it tried.

**Key derivation and the honest recovery tradeoff.** A dedicated vault passphrase (deliberately separate from the Supabase login password — a Supabase password reset shouldn't silently orphan vault documents) is run through PBKDF2-SHA256 (250,000 iterations, native `crypto.subtle.deriveKey`, `extractable: false` — the raw key bytes can never be read back out even by RicherWealth's own frontend code) against a per-user salt. The salt is not secret and is stored server-side (`User.vaultKeySaltB64`) so the same key re-derives deterministically on any device. **The passphrase itself is never sent to or stored by the server in any form.** This means: if a user forgets the vault passphrase, every document they've encrypted is permanently undecryptable — there is no server-side recovery, because true zero-knowledge means the server never had the key to recover with. The setup screen states this plainly, not as a buried disclaimer: *"Store this passphrase safely — RicherWealth cannot recover it... there is no 'forgot passphrase' recovery, because a real recovery option would mean the server could read your files, which defeats the entire point of a zero-knowledge vault."* A required checkbox ("I understand that if I lose this passphrase, my vault documents are permanently unrecoverable") gates the "Create vault" button.

**Unlock verification via an encrypted canary, not by guessing.** At setup, a known constant string is encrypted with the freshly-derived key and stored (`User.vaultCanaryB64`/`vaultCanaryIvB64`) — non-secret, reveals nothing about the passphrase or any document. The "Unlock vault" screen re-derives a key from the re-entered passphrase and tries to decrypt the canary: AES-GCM is authenticated, so a wrong key fails the auth-tag check and `subtle.decrypt` REJECTS rather than returning corrupted-but-plausible plaintext — verified live in the browser (typed a deliberately wrong passphrase, got "Incorrect passphrase." immediately, no silent garbage).

**Filenames are encrypted too, not just file content.** A filename like "Aadhaar_1234.pdf" is itself PII-bearing. `VaultDocument.encryptedFilename`/`encryptedFilenameIv` hold an AES-GCM ciphertext of the original filename, decrypted client-side for display (`DocumentRow` in `vault/page.tsx`) — the plaintext filename never appears in any server-visible location, including the storage path itself, which is a random UUID (`getVaultUploadUrl`, `storage.service.ts`) rather than the `{timestamp}_{sanitizedFilename}` pattern the older asset-documents/tax-documents buckets use. `mimeType`/`fileSizeBytes` are stored in the clear (low-sensitivity technical metadata, same precedent as `ItrDocument`).

**Category → Asset linking: only where a real model exists to link to.** PAN/Aadhaar/Passport/Tax Returns are category-tagged only — Tax Returns is deliberately standalone even though Phase 15's `ItrDocument` exists, since a vault upload is "a scan for safekeeping" and an ITR upload is "a parsed, reviewed structured record," and conflating the two would misrepresent what's actually in a vault row. Insurance is also tag-only because **no `Insurance` Prisma model exists anywhere in this app** (confirmed by grep — only `Asset` at `schema.prisma:244`) — inventing one for this alone was out of scope. Only Property Documents and Investment Statements get an optional `linkedAssetId` FK to a real, owned `Asset` row (ownership checked in `VaultService.register`, matching this repo's existing ownership-check convention).

**Verified empirically, not just unit-tested — this is the part that actually matters for a "zero-knowledge" claim.** Beyond the crypto module's own Jest suite (below), the live claim was checked three independent ways against the real running dev environment, with a distinctive marker string (`RICHERWEALTH_VAULT_PLAINTEXT_MARKER_7f3a9c2e`) planted in a test file specifically so its absence could be asserted, not assumed:
1. **Network**: monkey-patched `window.fetch` in the live browser tab to intercept the actual `PUT` to Supabase Storage's signed-upload URL. The uploaded body was 933 bytes (917-byte plaintext file + 16-byte AES-GCM auth tag — the arithmetic matches exactly) of binary noise; the marker string does not appear anywhere in it.
2. **Database**: queried the live Postgres `vault_documents` table directly via `psql` — every row's `encryptedFilename`/`iv`/`storagePath` is ciphertext/random-UUID, no readable filename or content in any column.
3. **Storage**: fetched the raw object from the `vault-documents` bucket directly with the Supabase service-role key (bypassing the app, and thus any possible decryption) — identical 933-byte ciphertext, marker absent, first bytes are high-entropy binary, not text.
4. **Full round-trip through the real UI**: uploaded the test file via drag-and-drop-equivalent through the actual `/vault` page, then decrypted-and-previewed it — the object-URL bytes served to the `<iframe>` were fetched and diffed against the original: 917 bytes, byte-for-byte identical, marker present (because this time it's the *decrypted* copy, correctly restored).

**A real, pre-existing bug found and worked around, not fixed (out of scope) — flagged for the user.** This dev environment's browser session had a genuinely expired Supabase auth session (the long multi-agent session that built Phases 14/15 had been running for hours). The login page's "Quick Demo Login (Skip Supabase Auth)" button (`apps/web/src/app/(auth)/login/page.tsx`, `handleDevLogin`) turned out to be dead/vestigial: it sets a raw `sb-access-token=dev-token` cookie that nothing on the backend or in `SupabaseAuthGuard` actually reads — `supabase.auth.getSession()` (used by every hook in this app, including this phase's `useVault.ts`) still returns no session afterward, and the button silently fails to authenticate. Confirmed via direct testing, not assumed. Real re-authentication was obtained the legitimate way: created a new, pre-confirmed test user via the Supabase Admin API (`auth.admin.createUser({ email_confirm: true })`, using the already-present `SUPABASE_SERVICE_ROLE_KEY` — the standard, sanctioned server-side flow for this, not a workaround), then signed in via the standard `POST /auth/v1/token?grant_type=password` endpoint with the real anon key. **One dead end deliberately not pursued:** an early attempt to self-sign a Supabase-compatible JWT using the project's `SUPABASE_JWT_SECRET` was correctly blocked by this session's own safety tooling as looking like credential forgery, even though the intent was benign (testing with a key already legitimately available) — abandoned in favor of the standard password-grant flow instead, which is not forgery. **The broken demo-login button itself is a real, pre-existing gap worth a future session's attention** — not touched here, since fixing unrelated login infrastructure was out of scope for a vault feature.

**Tests.** `packages/shared-types/src/vault/crypto.spec.ts`: 9/9 — byte-for-byte round-trip on both small (14-byte, deliberately including null/high bytes) and larger (10KB) payloads, filename round-trip via `encryptText`/`decryptText`, key-derivation determinism (same passphrase+salt → same key, proven behaviorally since `CryptoKey` isn't `extractable`/comparable — data encrypted under one derivation decrypts under a second derivation from identical inputs), a different passphrase producing a different (non-interoperable) key, wrong-passphrase rejection (the acceptance criterion — asserts the decrypt promise rejects, never resolves with garbage), tampered-ciphertext rejection (GCM auth-tag integrity), and fresh-IV-per-call (same plaintext encrypted twice produces different ciphertext). `packages/shared-types/src/vault/types.spec.ts`: 4/4 — the category→asset-link matrix (explicit true/false for every category, not a default), Zod schema coverage. `packages/shared-types` full suite: **121/121**, run directly via `npx jest`. `apps/api` full suite: **243/244** (1 pre-existing skip from Phase 15, unrelated), unaffected by this phase — no backend-only vault unit tests were added beyond what the acceptance criteria required, since the round-trip/determinism/wrong-passphrase logic is fully covered by the shared crypto module's own suite and the live empirical checks above cover the integration surface a unit test can't (real network bytes, real DB, real storage object).

**Left undone / known gaps, stated plainly:**
- No key-rotation or multi-device-passphrase-change flow — changing the vault passphrase isn't supported; doing so would require re-encrypting every existing document client-side with a new key, which this phase doesn't build.

**Net-worth math — the actual design decision the acceptance criterion hinges on.** A joint asset shows at its **full** value in every household member's own dashboard (a spouse sees "our house" as the real $500k, not a fraction) — `NetWorthService.calculateNetWorth(userId)` was extended to union the caller's personal (non-household) rows with every row owned by any household they belong to.
